### P0 - Runtime session state is unsynchronized across concurrent execution contexts (2026-06-12 review)
`TranscriptionSessionRuntime` (plain class, no actor/locks) has its mutable state (`state`, `stopping`, `latestPartialTranscript`, `suppressLateProviderPartials/Finals`, `pendingSubmissionInProgress`, etc.) mutated from four concurrent contexts: the UI's detached start task, a separate detached stop task, the URLSession WebSocket receive task (partial/final/error handlers), and per-buffer audio tasks. Worst concrete races: (a) `VoiceCommandStateMachine.buffer` is appended by `processFinal` on the receive task while `drainForShutdown` reads+clears it on the stop task — a late provider final racing a release submission can deliver the user's sentence twice or corrupt/crash mid-release (`TranscriptionSessionRuntime.swift:278-296, 563-605`; `ProtocolStateMachine.swift:108-193`); (b) the `stopping`/`stopped` double-stop guard is check-then-act with the flag set only after a long await, so two stops can tear down concurrently (`TranscriptionSessionRuntime.swift:403-443`); (c) start/stop interleaving can leave the AVAudioEngine running with the mic indicator on after the UI shows idle, or leak a live authenticated provider WebSocket (`TranscriptionSessionRuntime.swift:306-364, 408-469`; `AVFoundationAudioSource.swift:65-74`; `SonioxTranscriber.swift:49-60`). Fix direction: make the runtime an actor (or confine all state to one serial executor) — mechanical but broad; needs its own plan.

### P1 - Audio chunks are forwarded in unordered per-buffer Tasks (2026-06-12 review)
`AVFoundationAudioSource.handleInputBuffer` spawns an unstructured `Task` per tap buffer (`AVFoundationAudioSource.swift:76-93`); unstructured tasks have no mutual ordering, so under send backpressure PCM chunks can reach the STT WebSocket out of order (garbled transcripts, unreproducible), tasks accumulate without bound, and the push-to-talk audio-gate check runs at task-execution time rather than capture time. Fix: feed buffers through an `AsyncStream` consumed by a single serial sender, applying the gate at capture.

### 2026-10-24 - Cancelled warm-session recycle timer fired immediately (orphaned warm session)

Under load the 1 ms `Task.sleep`-based wait overshot past 5 ms, so the partial arrived while the runtime was still waiting for the provider final; at that point it is, by design, newer text (`shouldAcceptProviderPartial` is true until the fallback sets `suppressLateProviderPartials`), so the fallback submitted "stale late partial" instead of "latest visible words" and both expectations failed. The runtime behaved correctly; the test encoded a race between two timers.

**Fix:** the test now emits the late partial and a late final only after `stop(...)` returns (the fallback submission completes inside `stop`), which is exactly the scenario the name describes, with no timers involved; it also asserts the late final is dropped. A new companion test, `sessionRuntimeFallbackUsesPartialReceivedDuringFinalWait()`, pins the in-window behavior (a partial received after `commit()` but before the timeout becomes the fallback text) using a 300 ms wait window, far above the mock's emission latency. Verification: 25/25 isolated runs of both tests; 6/6 full-suite runs (230 tests) with four CPU hogs running. The `partialAfterCommitDelayNanoseconds` mock knob is kept for the new test's sibling scenarios but no longer used. The broader P0 "runtime session state is unsynchronized" item is unaffected and stays open; the pipeline's `--skip-tests` reruns of builds 12 and earlier are no longer needed.

### 2026-06-20 - ax-value delivery wiped rich-text formatting (Outlook email body)

**Issue:** Dictating into an open Outlook email broke the message's formatting on insert — as if formatting information was carried in with the plain text. Reproduced via the latency log, which showed Outlook's compose body is delivered to with `"method":"ax-value","target_role":"AXTextArea"`.

**Root cause:** `FocusedInputHelperMain.axInsert` (`Sources/UntypeCore/FocusedInputHelper.swift`) inserted text by reading the **entire** `kAXValueAttribute` as a flat `String`, splicing the new text into it, and writing the whole field back as a plain `CFString` via `AXUIElementSetAttributeValue(..., kAXValueAttribute, ...)`. For a rich-text field with a settable `AXValue` (the Outlook HTML/RTF compose body), this replaced the entire formatted body with its plain-text equivalent, wiping fonts, bold/italic, colors and signature styling across the whole email.

**Fix (final, after on-device probing):** `axInsert` now (1) inserts at the caret via `kAXSelectedTextAttribute` instead of round-tripping the whole `kAXValueAttribute`, and (2) **verifies the insertion actually happened** by comparing the `AXValue` UTF-16 length before/after the write. The destructive whole-value rewrite was removed entirely.

The verification step was essential: on-device probing (via `test_scripts/outlook-input-probe.sh` against the Accessibility-trusted bundled helper) showed the current Outlook compose body **accepts the `AXSelectedText` write and returns `.success` while inserting nothing** (a silent no-op). Without the length check, `deliverAuto` treated that as a successful delivery and stopped — so dictated text never appeared in Outlook even though the log showed `method:"ax-value","ok":true`. With the check, the no-op is detected (unchanged length → throws `selected_text_noop`) and auto-delivery falls through to `paste-keycode`, which the same probing confirmed both **lands in Outlook and preserves formatting** (as does `unicode-events`). The length check only fires on an *unchanged* length, so a legitimately replaced selection (which changes length) is never mistaken for a no-op and text is never double-inserted. Added an `ax_selected_text_settable` field to the helper `diagnose` output for future debugging.

`swift build` green; full `swift test` 216/216 pass. Probe results: `unicode-events` and `paste-keycode` both inserted the probe text into Outlook with formatting preserved; the old `ax-value` whole-value path was the sole cause of the formatting break.

### 2026-06-12 - Live voice commands now execute immediately (Soniox `<end>`/`<fin>` flush fixed)

Resolved the reported issue where spoken protocol commands such as `command send` and `command status` were not acted on while speaking and only appeared to activate when the CLI session was terminated with Ctrl+C.

**Issue.** Protocol actions execute only on *final* transcripts (`VoiceAgentProtocolController.final`). The live path added on 2026-05-26 (detect an actionable command in a partial transcript → ask the provider to commit via `SonioxTranscriber.commit()` → `{"type":"finalize"}`) worked up to the finalize request, but the finalize *response* was never recognized. The Swift Soniox adapter flushed committed finals only when a frame arrived with top-level `"type":"endpoint"` or `"type":"finalized"` — message shapes the raw Soniox realtime WebSocket protocol never sends. Soniox signals these boundaries as `<end>` (endpoint detected) and `<fin>` (finalize complete) **marker tokens inside a regular `tokens` frame**; the official `@soniox/node` SDK (used by the TypeScript source project) synthesizes its `endpoint`/`finalized` events from exactly those tokens. The Swift port filtered `<end>`/`<fin>` out of the transcript (correct) but never used them as a flush trigger (the bug), so committed finals accumulated until the `finished` frame at session shutdown — which is why commands executed only at Ctrl+C. The same defect explains why UI push-to-talk releases always logged `text_source: quick_close_partial`: provider finals never arrived live, and Quick Close masked the failure by submitting partials.

**Solution.** `SonioxTranscriber.handleTokens` now reports when a frame carries an `<end>`/`<fin>` utterance-boundary marker, and `handleTextFrame` flushes committed finals immediately in that case, mirroring the SDK's event synthesis. The defensive handling of typed `endpoint`/`finalized`/`finished` frames is retained. ElevenLabs was audited and is unaffected (its protocol genuinely delivers typed `committed_transcript` messages). Added regression tests covering `<end>`-token and `<fin>`-token flushes (`SonioxTranscriberTests.swift`); `swift build` and `swift test` pass (172/172), including the push-to-talk runtime suite. Repackaged `/Applications/untype.app` (build 2, unsigned local) so the UI and the `~/.local/bin/untype` CLI symlink both carry the fix; the running app instance must be quit and relaunched to pick it up.

Resolved a native UI focused-input issue where processed output could be produced and copied but not inserted into the intended edit control because `untype.app` had regained foreground focus before the input operator delivered text, or because UI mode still routed delivery through `untype-input-helper` and macOS rejected that helper for Accessibility.
